# Аудит безопасности TodoApp

**Дата:** 2026-10-27  
**Область:** backend (.NET 10), конфигурация, Docker, Bruno, файлы IDE.  
**Статус:** только анализ и read-only проверки; существующие данные не читались и не изменялись. Значения секретов в документе не приводятся.

## Краткое резюме

Найдено 3 критических, 5 высоких и 5 средних проблем. Главная — скомпрометированный JWT-секрет: с ним можно выпустить токен для любого пользователя и получить полный доступ к его заметкам и задачам. Секрет лежит в `.env` и используется запущенным контейнером.

В ходе проверки:

- запрос без токена → `401`;
- токен, подписанный ключом из `appsettings.json` → `401`;
- токен, подписанный `JWT_SECRET` из `.env`, с произвольным `nameidentifier` → `200 OK`;
- логин несуществующего пользователя → `500`;
- `GET /openapi/v1.json` → `200`, `/scalar` → `302`;
- `dotnet list package --vulnerable --include-transitive` — уязвимых NuGet-пакетов не найдено.

## Критические

### 1. Компрометация JWT-секрета → обход аутентификации

**Где:**

- `.env:2`
- `docker-compose.yml:29`
- `backend/WebAPI/Program.cs:17-31`
- `backend/Auth/Services/AuthService.cs:23-38`

**Описание:**

В переданной папке находится рабочий `JWT_SECRET`, и контейнер использует именно его. Токен с произвольным `nameidentifier`, подписанный этим секретом, принимается API. Это позволяет действовать от имени любого пользователя: читать, изменять и удалять чужие заметки и задачи.

**Подтверждение:**

```text
GET /Note без токена                                  -> 401
GET /Note с токеном на ключе из appsettings.json      -> 401
GET /Note с токеном на JWT_SECRET из .env             -> 200
```

**Последствия:** полный обход аутентификации для любого, у кого есть папка/архив проекта или иной доступ к `.env`.

**Исправление:**

1. Немедленно сменить `JWT_SECRET`.
2. Перезапустить API, чтобы старые токены перестали действовать.
3. Удалить `.env` из всех передаваемых копий и архивов.
4. Хранить секрет в Docker secrets или user-secrets.
5. Добавить fail-fast проверку: секрет обязателен, не равен placeholder, имеет достаточную длину и энтропию.

### 2. Секреты в открытом виде

**Где:**

- `.env:1-2` — `DB_PASSWORD` и `JWT_SECRET`;
- `backend/.idea/.idea.Todo/.idea/dataSources.xml:9`;
- `backend/.idea/.idea.Todo/.idea/dataSources/data_sources_history.xml:12` — тот же пароль БД.

**Описание:**

`.gitignore` игнорирует `.env` и `.idea`, но это не защищает файлы, если папка уже заархивирована, передана кому-либо или если файлы когда-либо попадали в git. Пароль БД продублирован в конфигурации IDE.

**Последствия:** компрометация БД и возможность подписи JWT.

**Исправление:**

1. Сменить пароль БД и `JWT_SECRET`.
2. Удалить `.env` и `.idea` из распространяемых копий.
3. При необходимости вычистить историю git.
4. Ограничить права на файлы (`chmod 600` на Linux).
5. Перейти на Docker secrets/user-secrets; не хранить рабочие секреты в IDE-конфигурации.

### 3. API работает по HTTP на всех интерфейсах

**Где:**

- `docker-compose.yml:30-31` — публикация `5000:8080`;
- `backend/WebAPI/Properties/launchSettings.json:8,17` — `0.0.0.0`;
- `backend/WebAPI/Program.cs` — нет `UseHttpsRedirection`/HSTS.

**Описание:**

Контейнер опубликован как `0.0.0.0:5000->8080` и `[::]:5000`. Пароли и bearer-токены передаются по сети открытым текстом.

**Последствия:** перехват учётных данных и токенов, повторное использование украденного токена.

**Исправление:**

1. Поставить TLS-терминацию (Caddy/Nginx/Traefik).
2. Включить `UseHttpsRedirection` и HSTS.
3. Для локального запуска публиковать только `127.0.0.1:5000:8080`.
4. Не публиковать dev-профиль на все интерфейсы.

## Высокий риск

### 4. Публично известный JWT-ключ по умолчанию

**Где:** `backend/WebAPI/appsettings.json:9`.

**Описание:**

При запуске без переменных окружения используется ключ `your_secret_key_minimum_32_characters`. Он известен, а `launchSettings.json` слушает `0.0.0.0` в режиме Development. README предупреждает о настройке, но приложение не проверяет конфигурацию и не падает.

**Исправление:** убрать рабочий ключ из `appsettings.json`, добавить проверку при старте, хранить секрет только в user-secrets/переменных окружения.

### 5. Нет rate limiting и блокировки попыток входа

**Где:**

- `backend/WebAPI/Controllers/AuthController.cs:11-23`;
- `backend/Auth/Services/AuthService.cs:16-54`;
- в `Program.cs` нет `AddRateLimiter`.

**Описание:**

`/Auth/login` и `/Auth/register` не ограничены. Это позволяет перебирать пароли, проводить credential stuffing, спамить регистрациями и нагружать CPU через BCrypt.

**Исправление:** ASP.NET Core Rate Limiter, lockout после неудачных попыток, задержки, CAPTCHA при подозрительной активности, мониторинг.

### 6. Нет валидации входных данных и политики паролей

**Где:**

- `backend/Auth/Dto/LoginDto.cs:5-6`;
- `backend/Auth/Services/AuthService.cs:41-54`.

**Описание:**

Принимаются пустые или очень короткие имена и пароли. Null-значения и слишком длинные строки приводят к `500`. Нет ограничений на длину username/password, нет нормализации.

**Исправление:** `DataAnnotations` или FluentValidation, `[Required]`, `[StringLength]`, минимальная длина пароля 12+, максимум 72 байта для BCrypt, правила для username.

### 7. Приложение работает в PostgreSQL как суперпользователь

**Где:** `docker-compose.yml:5-7,25-28`.

**Описание:**

`POSTGRES_USER=todo` создаёт суперпользователя, и API подключается этим же пользователем. При компрометации приложения или появлении SQL-инъекции это даёт доступ к другим БД, созданию ролей и `COPY ... FROM PROGRAM`.

**Исправление:** отдельная роль для API с правами только `SELECT/INSERT/UPDATE/DELETE` на `tododb`; административная роль — отдельно.

### 8. Раскрытие существующих пользователей

**Где:** `backend/Auth/Services/AuthService.cs:20,43-45`.

**Описание:**

При логине для несуществующего пользователя BCrypt не вызывается из-за короткого замыкания `user == null || ...`, поэтому ответ заметно быстрее. При регистрации явно возвращается ошибка о существующем имени. Это позволяет перечислять пользователей.

**Исправление:** для отсутствующего пользователя выполнять проверку фиктивного BCrypt-хэша, всегда возвращать одинаковый ответ, не раскрывать причину ошибки регистрации.

## Средний риск

### 9. Необработанные исключения → `500`

**Где:**

- `backend/Auth/Services/AuthService.cs:21`;
- `backend/BusinessLogic/Services/NoteService/NoteService.cs:29,39,48,65`;
- `backend/BusinessLogic/Services/TaskService/TaskService.cs:29,39,50,66`;
- в `Program.cs` нет глобального обработчика.

**Описание:**

Логин несуществующего пользователя возвращает `500`, а не `401`. «Note not found» и «Task not found» дают `500` вместо `404`. В Development это может раскрывать stack trace и детали SQL.

**Исправление:** глобальный exception handler + `ProblemDetails`; маппинг `UnauthorizedAccessException` → `401`, not found → `404`, duplicate → `409`; не отдавать наружу текст исключений.

### 10. Слабая проверка JWT и долгий срок жизни

**Где:**

- `backend/WebAPI/Program.cs:23-31`;
- `backend/Auth/Services/AuthService.cs:32-38`.

**Описание:**

`ValidateAudience = false`, токен живёт 24 часа, нет `jti`, нет механизма отзыва. Если тот же ключ используется в другом сервисе, его токены будут приняты. Украденный токен действует сутки.

**Исправление:** включить `ValidateAudience` и `ValidAudience`, сократить TTL, добавить refresh-токены/отзыв, `ClockSkew`, `ValidAlgorithms = [HmacSha256]`.

### 11. `.dockerignore` пропускает чувствительные файлы

**Где:**

- `backend/.dockerignore:1-5`;
- `backend/Dockerfile:10`.

**Описание:**

Не исключены `.env`, `appsettings.*.json`, `.git`. При `COPY . .` и `dotnet publish` секреты из `appsettings.Development.json`/`Production.json` могут попасть в build cache или итоговый образ.

**Исправление:** добавить в `.dockerignore` `.env`, `appsettings.*.json` (кроме базового), `.git`, IDE-файлы, тесты; проверять содержимое образа.

### 12. OpenAPI/Scalar доступны без авторизации

**Где:** `backend/WebAPI/Program.cs:73-74`.

**Описание:**

`GET /openapi/v1.json` → `200`, `/scalar` → `302`. Схема API раскрывает все маршруты и модели. Security-заголовков нет: в ответе только `Server: Kestrel`, без HSTS, CSP, `X-Content-Type-Options`.

**Исправление:** отключить или ограничить документацию в production, добавить security headers, скрыть лишние заголовки.

### 13. Нет пагинации и ограничений на объём данных

**Где:**

- `backend/WebAPI/Controllers/NoteController.cs:21-27`;
- `backend/WebAPI/Controllers/TaskController.cs:29-35`;
- `backend/DataAccess/Data/AppDbContext.cs:16-17,26-27`.

**Описание:**

`GET` возвращает все записи пользователя. Лимиты длины строк есть только в БД, но не в DTO, поэтому слишком длинные значения дают `500`. Нет квот на количество заметок/задач.

**Исправление:** пагинация, лимиты размера запроса, валидация длины, квоты и rate limiting для авторизованных пользователей.

## Низкий риск и hardening

- В `bruno/TodoWebApi/Note/Create note.yml:11` и `bruno/TodoWebApi/Task/Create task.yml:11` захардкожен Bearer-токен. Он истёк `2026-05-08 13:08 UTC` и не подписан текущим `.env`-секретом, но его нужно удалить; если он когда-то был рабочим, считать аккаунт `test` скомпрометированным.
- Потенциальный stored XSS, если появится UI, который рендерит `Name`/`Text` как HTML. Сейчас фронтенда в проекте нет; при добавлении использовать экранирование и CSP.
- В `backend/DataAccess/Data/UserRepo/UserRepository.cs:33` логируется имя пользователя; DTO-записи с `Password` при случайном логировании раскроют пароль через `ToString()`. Не логировать DTO и добавить redaction.
- `backend/BusinessLogic/BusinessLogic.csproj:12-15`: `InternalsVisibleTo("xUnit-Tests")` без strong name.
- `TaskProgressStatus` принимает произвольные числа (`TaskDtos.cs:6-7`, `TaskService.cs:54,75`) — добавить `Enum.IsDefined`.
- `UserModel.PasswordHash` не помечен `[JsonIgnore]`; сейчас не утекает, но это защита на будущее.
- `backend/DataAccess/Extensions.cs:17`: строка подключения собирается интерполяцией; лучше `NpgsqlConnectionStringBuilder`.
- `backend/Dockerfile:1,13` и `docker-compose.yml:3` используют плавающие теги; закрепить digest и добавить сканирование образа (Trivy).
- Нет `read_only`, `cap_drop`, `no-new-privileges` в compose; `USER app` в Dockerfile — хорошо.

## Что проверено и находится в порядке

- **IDOR:** заметки и задачи фильтруются по `UserId` из JWT; при честном токене чужой объект не доступен.
- **SQL-инъекции:** EF LINQ с параметризацией; raw SQL только константный `SELECT 1`.
- **Mass assignment:** DTO не содержат `UserId`, `ItemId`, `Created`.
- **Пароли:** BCrypt с солью.
- **CSRF/CORS:** токен передаётся в заголовке, cookie нет; CORS не настроен.
- **NuGet:** `dotnet list package --vulnerable --include-transitive` — уязвимых пакетов не найдено.
- **БД:** порт `5433` опубликован только на `127.0.0.1`.
- **Контейнер API:** запущен не от root.

## Приоритетный план

1. Сменить `JWT_SECRET` и `DB_PASSWORD`, перезапустить API, удалить секреты из всех копий.
2. Закрыть API TLS и убрать публикацию на `0.0.0.0`.
3. Убрать дефолтный JWT-ключ и добавить fail-fast проверку конфигурации.
4. Добавить rate limiting, lockout, валидацию и политику паролей.
5. Добавить глобальный обработчик ошибок и корректные статусы.
6. Включить audience validation, сократить срок токена, добавить отзыв.
7. Выделить least-privilege роль БД, поправить `.dockerignore`, ограничить OpenAPI/Scalar.
